# Android configuration apply latency and later journal write failure (read-only, r2)

## Scope and evidence

I inspected only the two supplied `/tmp` journal copies, `/tmp/github-v2-android-apply-io.json`, `/tmp/github-v2-restart-failure-result.json`, and repository source. I did not access the device, CDP, remote, vault, or modify the repository. The journal copies are point-in-time snapshots; the first was captured during a configuration apply. Counts below describe those copies, not a later live journal. I did not print file contents or paths from retained evidence.

The first copy, `/tmp/github-v2-android-journal-latency-r2`, has 11 native records (sequences 78–88), 11 native content objects, 12 retained hold files, 13 engine records (209–221), and 39 engine objects. All copied record-name SHA-256 hashes and object-name SHA-256 hashes match their bytes. Native record 88 has no pending intent or recovery issue, 12 tracked holds, and **21 nested `Entry.data` references to 9 distinct object hashes**. Its engine counterpart, record 221, has **38 `blobs` references to 38 distinct hashes** and a configuration operation with one applied step. This confirms that the earlier engine duplicate-object hypothesis does not apply; the duplicate references are in native state.

The newest eight native records (81–88) contain **160 object references**. There are **64 distinct hashes when counted separately within each record**, and 10 distinct hashes across all eight. The current `FileJournalStore.compact()` deliberately verifies each retained record separately; `unpack()` serially reads each nested reference, including repeats (`plugin/src/git-sync/store.ts:122–153,199–223`). `GitObsidianVault.recoverNative()` always invokes this compact pass (`obsidian-vault.ts:359–404`), and `SyncSession.applyConfiguration()` enters native recovery before applying the reviewed step (`session.ts:485–509`). Therefore this exact snapshot would cause **160 serial native object reads in one compact pass**. The root's partial probe of 88 serial reads in about 21 seconds is consistent with an unfinished portion of that pass; the probe lacks paths/stacks, so it does not prove which 88 reads they were.

## Exact production-store benchmark

`/tmp/github-v2-android-journal-bench-r2.ts` preloads the supplied bytes into a memory-backed `JournalFiles` adapter, applies a 24 ms delay to each adapter call, and invokes the repository's **unmodified production `FileJournalStore`**. Compaction and changed saves mutate only that memory map. The changed saves alter metadata only; an actual native `begin` adds entry references. This tests store call counts and scheduling against the copied production journal; it is not an Android speed test. The `native load` row represents journal opening, which ordinarily happens at plugin startup, not each apply click.

| Operation on copied journal | All adapter calls by method | Object calls | Peak calls | Delayed bench |
|---|---|---:|---:|---:|
| Native load, latest 88 | 5 exists, 1 list, 22 read | 21 reads | 1 | 722 ms |
| Native compact, newest 8 | 15 exists, 6 list, 168 read, 4 remove | **160 reads** | **1** | 4,821 ms |
| Native changed save | 32 exists, 2 list, 23 read, 1 write, 1 rename | 21 exists + 21 reads | **1** | 1,479 ms |
| Engine load, latest 221 | 5 exists, 1 list, 39 read | 38 reads | **4** | 429 ms |
| Engine changed save | 49 exists, 2 list, 40 read, 1 write, 1 rename | 38 exists + 38 reads | **4** | 927 ms |

At an illustrative **high-latency-run** 240 ms per adapter call, the native compact pass has **38.4 seconds of object reads alone** (160 × 240 ms), or **46.3 seconds** if all 193 adapter calls cost 240 ms and remain serial. This is a conditional synthetic model, not a measured device duration or an intrinsic storage cost. A changed native save similarly has 42 serial object checks, or 10.1 seconds for those checks alone at that call latency. The successful hidden rename path can durably save at `begin`, `markAttempted`, and `finish` (`native-transactions.ts:287–333`), each packing the current native state. A successful one-step configuration operation also saves engine approval, step outcome, and retirement (`session.ts:522–526,1750–1766`). Capture, namespace inventory, native file I/O, and UI loads add costs that this benchmark does not measure.

## Small optimization supported by this fixture

Pass a **per-`pack()` invocation** map from body string to the pending `digest`/`put` promise, and a **per-`unpack()` invocation** map from hash to the pending read/checksum promise. Reuse these only for repeated references encountered in that one invocation. `compact()` calls `unpack()` separately for each retained record, so every retained record still reads and SHA-256-verifies each distinct object it references. Preserve both `assertHead()` calls, record readback, the outer journal queue, and all existing failure handling. Do not retain values across operations or across retained records. This extends the already-used per-table `blobs` pending-map pattern (`store.ts:99–117`) to recursive `Entry.data` references.

I tested that shape in an **unshipped `/tmp` source copy**, `/tmp/github-v2-store-dedupe-r2.ts`, using the same exact journal adapter and 24 ms delay (`/tmp/github-v2-android-journal-bench-dedupe-r2.ts`). Native load fell from 21 to 9 object reads; compact from **160 to 64**; changed save from 21 exists + 21 reads to **9 exists + 9 reads**. The copied engine fixture retained its 38 distinct-object counts and four-call peak. The prototype compact run was 2,515 ms instead of 4,821 ms at the synthetic delay. At 240 ms per call, 96 fewer compact reads would remove **23.0 seconds of modeled adapter wait**; 12 fewer read pairs per changed native save would remove **5.8 seconds**. These are call-count projections, not Android speed claims. A production implementation needs exact round-trip, corruption-on-load/save, interrupted-write, stale-writer, and concurrent duplicate-reference checks before deployment. Further overlap of distinct nested references needs a shared global four-call limit; naïve nested pools could exceed the current IO4 bound.

## Independent failure after full restart

The later result, `/tmp/github-v2-restart-failure-result.json`, reports all 30 recorded pre-failure checks passing, including the guarded configuration behavior, then fails during unrelated note sync with **`Recovery write verification failed. Sync stopped.`** The second copy, `/tmp/github-v2-android-journal-write-failure`, has one **zero-byte engine record temp** for sequence 226, no committed record 226, and a valid latest committed record 225. All 17 copied committed engine record hashes and all 41 engine object hashes validate; every engine object is referenced by at least one copied committed record. The latest committed state has no open operation. The temp is a record temp under `records/`, not an object temp under `objects/`.

`FileJournalStore.put()` writes the temp, immediately reads it back, compares exact text, then renames it (`store.ts:68–80`). The message can arise only when that read returned a different string after `write()` resolved. The zero-byte temp is consistent with an acknowledged write that left an empty file, but the snapshot alone cannot distinguish early acknowledgement/read visibility, a truncated/failed underlying write, or host interruption during that write. `PluginOwnership.fence()` checks ownership before an adapter method call; a retired owner at the following `read()` would throw its own retirement error, not this verification message (`ownership.ts:130–140`). The four-worker object pool finishes before record `put()` starts (`store.ts:254–265`), and its paths are under `objects/`; it is not the immediate writer of this temp.

`/tmp/github-v2-record-empty-write-repro-r2.ts` loads the second exact copy into memory, injects one record-temp `write()` that resolves after storing an empty string, and runs unmodified production `FileJournalStore.save()`. It reproduces the **exact error**, leaves one new zero-byte temp, keeps committed sequence 225 as head, and creates no record 226. This establishes that the readback check caught this failure and preserved the prior journal head; it does **not** establish why the real Android adapter produced zero bytes. Do not bypass the readback or treat an empty temp as a committed record.

## Successful ordinary Sync now retry

The root later reported a successful production UI retry: `Changes published · 1 held files pending`, with automatic sync still paused. `/tmp/github-v2-journal-retry-io.json` contains 39 timed **record** calls over a 14.3-second event span: 33 reads (median 1 ms, maximum 4 ms), three record-temp writes (4–5 ms, lengths 37,834, 37,636, and 32,060 characters), and three renames (3–11 ms). Each temp readback returned its full input length before rename, and each committed record readback returned the same length. Sixteen native record reads had a median 1 ms method duration and 18 ms gap between starts. The event span includes other work between logged calls; it is not summed record-I/O time. The retry produced records 226–228 with different contents from the earlier failed 226 temp.

This shows the ~240 ms per-call observation was **run-dependent**. The journal's repeated serial native reads amplify slow calls, but the available evidence does not establish that Android storage is intrinsically slow or that the storage problem has been fixed. UI scheduling, bridge queuing, background throttling, and adapter write behavior remain hypotheses. The successful retry confirms that keeping immediate readback allowed progress when bytes were actually present; the first failure remains independently documented.

### Focused Android follow-up for the root

On an isolated disposable journal namespace and with the same production adapter, instrument only metadata around one record-temp `write`/`read`: intended UTF-8 byte length and SHA-256, `write` start/resolve times, immediate `read` length/hash, `stat` size, then a delayed second `read`/`stat` **for diagnosis after a mismatch**. Record app foreground/background/reload events and free-space/write exceptions. If the delayed read fills in, investigate adapter acknowledgement or read visibility; if it stays zero, investigate write failure/truncation or host interruption. Keep the existing immediate exact readback as the gate and preserve the failed temp and prior record for review. The cleared IO probe cannot be used to attribute this later failure to the earlier latency trace.

To isolate the 240 ms timing, run the same read-only native-record/object sequence on an isolated copied journal through the production adapter under both ConfigurationModal and ordinary Sync now, while recording `performance.now()` at the store call boundary, adapter entry/resolve, and animation-frame gaps. Match call count, file size, host foreground state, and running plugins; compare per-call duration with gaps between calls. The root owns that live experiment. The present snapshot proves the multiplicative call pattern and the two observed timing regimes, not which Android scheduling layer caused the slow regime.
