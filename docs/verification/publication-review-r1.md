# Publication v2 engine review, round 1 (commit 9d9816b, /tmp/vault-sync-publication-v2)

Scope: `contracts.ts`, `github.ts` (publish/seal/readLedger/prepare), `state.ts`, `session.ts`, `reconcile.ts`, `test/git-fakes.ts`, `test/git-session.test.ts`, `test/git-reconcile.test.ts`, read against `/tmp/github-v2-design-opus-r1.md`, `/tmp/github-v2-native-review-r1.md`, `/tmp/github-v2-native-port.md`. Read-only; no repository edits, no remote or vault writes. Baseline: `npx tsx --test test/git-session.test.ts test/git-reconcile.test.ts test/engine.test.ts test/github-client.test.ts` = 170/170 pass on 9d9816b.

Scratch repros in `/tmp/vsp/` (`harness.ts` mirrors the test file's `device`/`enrolled`). Run from the worktree: `cd /tmp/vault-sync-publication-v2/plugin && npx tsx --test /tmp/vsp/<file>.test.ts`. R1 fails on purpose (it asserts the behaviour the engine should have); every other file passes and prints its evidence.

## Verdict

- **Ledger protocol (late publication vs seal, atomicity, read-back, restarts, no replay): PASS** under every modelled fault. Both delivery orders with a crash between the sealing save and the seal dispatch (R4), plus 400 random schedules mixing publish/seal faults (`before`/`after`/`error-after`/`delay`/`reject`), ledger outages, save crashes before/after, restarts and late deliveries (R8): no candidate appears twice on the branch, every candidate on the branch has its receipt in the ledger chain and vice versa, every recorded anchor stays in the final fast-forward chain, every run converges and never pauses. 10 delayed requests landed late in R8 and were all accounted for correctly.
- **Native holds (durable before ack, never merged/published, unrelated paths continue, release only after the exact write): PASS for safety, FAIL for liveness.** The first decision a user records on a hold created inside an operation is silently discarded (F1 below). Safety: a decided hold whose publication loses the race keeps the hold and re-asks without publishing the torn bytes (R5); a decided hold whose CAS write fails stays held (R5b); a hold on a remotely deleted path releases only after the exact delete (R5c).
- **Exact-version consent, bulk-deletion and rename heuristics: PASS** as designed, with two design/implementation gaps noted (F4, F6).
- **Stale ledger reads: fail closed, but to a sticky manual pause** that a plain retry never clears (F2). A single stale `absent` read after a landed publication turns an accepted commit into a reviewed "ledger-diverged" recovery.
- **Migration /2 unfenced request: hazard confirmed (worker's report is right).** Severity MEDIUM, concrete fence fix below (F3) that removes the review entirely.
- **Full self-contained Obsidian Git replacement on Android:** not claimed by this review. The engine side is sound; root wiring, N1–N3 and the native F1/F2 contract are still open and outside this scope.

No finding is a data-loss or replay defect; nothing warranted an early send.

## Findings (priority order)

### F1 — HIGH (liveness/UX, no data loss): the first decision on a hold raised inside an operation is silently dropped, and the re-asked conflict shows GitHub's version as `base`
- `session.ts:576-602`: the review (and every native conflict id, `reconcile.ts:319`, which hashes `base`) is computed from the effective base = checkpoint + carry. For an `interrupted`/`changed` step the carry origin is `expected` (`session.ts:991`), so the user sees `base = E`.
- `session.ts:611-622`: in the same `#transact` pass (reached through `#withHolds`, `:708-717`), "no outgoing, no incoming" is not `settled` because the carry is non-empty, so `state.carry = dictionary()` drops the held path's origin after the review was built. From then on the effective base for that path is the target commit's version `r`.
- `session.ts:989-1008`: `#applySteps` rebuilds `carry` from scratch, so the same drop happens whenever any later apply operation completes while a hold exists.
- Next `sync()`: `reconcile` produces a different id (base is now `r`), `session.ts:583-584` deletes the recorded decision as "stale", and the user is asked again with a misleading `base`.
- Repro `/tmp/vsp/r1-hold-decision-drift.test.ts`: interrupted write on `n.md`, resolve the first reported conflict with `next`, sync → `needs-decision` again, new id, `decision for first id still stored? false`, stored carry `{}` while the shown conflict's base was the original E. The existing F1 test masks this with `for (round < 2) a.restart().sync()` (`git-session.test.ts:1697-1700`) and by reading the id from `status()` after a second sync; `R5` in my scratch also needed that workaround.
- Fix: make the hold carry its own `base` (capture the effective base at ingestion in `StoredHold`, parse it in `state.ts:428-439`, include it in `referencedBlobs`, and have `nativeConflict` use `hold.base` instead of the plan base). That makes the id independent of checkpoint drift. Alternative (smaller, but leaves the `#applySteps` recompute to handle): preserve `carry[path]` for every held path at `:621-622` and in `:989-1008`. Add a test: decide from the first `needs-decision` outcome without a restart and expect `synced`.

### F2 — MEDIUM: one stale ledger read turns a landed publication into a manual "ledger-diverged" recovery
- `session.ts:808-819`: a value older than the anchor is re-read once (round 0 only); an `absent` read with a non-null anchor is never re-read (`value !== null` fails) and goes straight to `#diverged`.
- `session.ts:883-904`: `#diverged` pauses `ledger-diverged` with the publish operation still in state. The pause is sticky; `sync()` returns `paused` forever (`:306-316`), and the only exit is `recoverPublication` + re-enrollment.
- Repro `/tmp/vsp/r3-stale-ledger.test.ts`: R3a: publication landed, response lost, one stale `absent` read → `paused ledger-diverged`, operation still `publish`, ledger actually equals the operation's receipt, retry sync stays paused, recovery preview offered. R3b: two consecutive stale "older" reads → same pause.
- Design §12 blocker 2 says read freshness must be measured; the engine should not depend on it. Divergence is a one-way door, so spend a few reads on it: in `#diverged` (or before calling it) re-read the ledger N times (3–5) with jittered backoff of a few seconds, treat `absent`-with-anchor like "older", and pause only if every read disagrees. Also consider: before pausing, if the fresh read shows the receipt, accept (already handled once the re-read sees it).
- Not unsafe: the pause never replays and the archived recovery keeps every byte. But the user pays a review for a GitHub replica hiccup.

### F3 — MEDIUM: /2 legacy request can land after "discard" + re-enrollment (worker's report confirmed); concrete fix
- `session.ts:842-856`: a legacy publication is held until reachable; nothing fences it (correct: the /2 request moved only the branch). `session.ts:510-539`: `recoverPublication` releases with the honest note that the request "cannot be cancelled". `git-session.test.ts:1484-1497` asserts the hazard as documented.
- Repro `/tmp/vsp/r6-legacy-fence.test.ts` (`fence=false`): record the /2 publication, crash, hold as `publication-unknown`, user types a newer draft, discards, re-enrolls (newer draft archived, vault back to `base`), then the old branch-only CAS `P→C` is delivered: it lands, the next sync adopts it and the vault shows `legacy candidate` that the user discarded. All bytes are archived; nothing silent is lost, but the explicit discard is reversed by a remote change the user cannot distinguish from another device's edit.
- Severity MEDIUM, not HIGH: one-time /2→/3 migration on beta vaults only; needs a request GitHub applies after the client gave up; outcome is a reverted discard with every version in recovery. Not LOW: the engine presents the reappearing candidate as ordinary remote content and overwrites the (archived) local base without a decision.
- Fix (the parent's "seal the branch with a no-op commit" is right, and it can remove the review entirely): in `#settleLegacy`, when the candidate is not reachable and `head == parent`, publish a **fence** through the v3 protocol: a commit `F` with `parent = P`, `tree = P.tree`, plus a receipt `[anchor?, F]`, via the ordinary `publish` CAS `branch P→F`, `ledger anchor→receipt`, then `#settle` as usual. Receipt ⇒ the branch is no longer at `P`, so the legacy request (`beforeOid = P`) can never land: clear the operation (local drafts are still local and re-plan into a fresh candidate; no review, no archive needed). Seal ⇒ re-read head: candidate reachable ⇒ accept; head at some `X ≠ P` ⇒ also fenced, clear; head back at `P` ⇒ retry the fence next sync. `fence=true` in R6 (modelled with `repository.push({})`) shows the old request fails to land and the vault stays converged. Needs `github.ts` `prepare` to accept an empty change set (skip `POST /git/trees` and reuse `parent.treeOid`; `:400-427` currently always creates a tree, and GitHub rejects an empty tree list) or a dedicated `createFence(parent)`. The only remaining boundary is an external rewind of the branch back to `P` after the fence, which nothing client-side can prevent; document it as such. If the parent prefers to keep the review for now, the minimal variant is the same fence inside `recoverPublication` before `pause` is set, still through the ledger protocol so it can itself be settled; it does change that method's "no remote writes" contract (`:503-509`).

### F4 — MEDIUM-LOW: design §4's "top-level folder vanishing is an adapter error" is not implemented; a vanished folder below the bulk threshold is published as deletions
- `session.ts:1080-1085`: `#guardCapture` only refuses a zero-file capture. Design §4 also promised to treat a whole top-level folder disappearing as a capture error ("covers Android storage loss and unmounted folders").
- Repro `/tmp/vsp/r9-misc.test.ts` R9b: 121-file vault, `attachments/` (20 files) vanishes → `synced`, `attachments/f0.md` gone from GitHub. Other devices will delete them locally on their next sync. Bytes stay in history (restorable per file), and the files republish when storage returns, but the v2 guarantee "deletions always need review" was removed on the strength of this guard.
- Fix: in `#guardCapture`, if every path under a top-level folder present in the effective manifest is absent from the capture and the folder had ≥ k files (k = 2 or 3 is enough), throw `VaultCaptureError`; or lower the bulk floor for whole-folder deletions. Add it to the reconcile/session tests.

### F5 — LOW: one malformed native issue from `recover()` blocks every `sync()` forever, including paused vaults
- `session.ts:303` runs `#recoverNative` before the pause and identity checks; `#ingest` (`:1046-1057`) throws `IntegrityError` on the first bad issue, acknowledging nothing, so the vault keeps returning it.
- Repro `/tmp/vsp/r2-poison-issue.test.ts`: a `found` whose oid does not match → three restarts all throw; after a repository identity change `sync()` still throws before reaching the pause logic. `status()` still works.
- The vault contract (port doc rules 2 and 5) puts correctness on the native side, and failing closed is right for forged bytes. But a single bug in the vault's evidence (or the >8 MiB open point in the port doc) makes the whole engine unusable with no user path. Fix: validate per issue, skip and surface bad ones (never ack them), ingest the good ones, and expose the failure in `status()`.

### F6 — LOW: `#withHolds` discards the reporting of the sync that just happened
- `session.ts:708-717`: when holds exist, the second `#transact` result replaces the `synced` outcome; `sync()` (`:347-353`) merges `published`/`carried` only from `#resume`. R9a: `fresh.md` is published, the outcome is `needs-decision` with no `published` flag and no `carried` list. Reporting only; the scheduler/UI may show "needs decision" and never "published". Return both (e.g. `needs-decision` with `published` and `carried` fields, or run the hold pass as a non-mutating reconcile).

### Observations (no action required, or product decisions)
- `reconcile.ts:146`: 9 of 10 files deleted locally is automatic (`bulkThreshold` floor is 25). Per design; small vaults get no bulk guard. R7a.
- `reconcile.ts:267-290`: the bulk guard's threshold excludes relocated files but the conflict's `paths` (and the `remote` restore) include them, so "keep GitHub's side" on a local bulk deletion that contained moves restores the moved files at their old paths beside the new copies. Duplicates, not loss.
- Rename heuristic (R7c, `reconcile.ts:154-199`): local rename / remote edit moves the edit (one `E→N` step at the new path, outgoing `A-`,`B+`); remote rename / local edit creates `B` first and deletes `A` with an exact CAS last; rename+edit on the renaming side correctly falls to `local-deleted-remote-edited`; rename vs remote deletion republishes the content under the new name; divergent renames keep both names. The "unique" rule is per byte-version among deleted/added sets, so a sibling file with identical bytes that was not deleted does not make the rename ambiguous (R7c "ambiguous" case is actually unambiguous and moves the edit). All defensible; none loses bytes.
- A folder move with CRLF normalisation (30 files) trips the bulk guard (conservative); a pure move does not. R7b.
- `enroll()` adopts whatever ledger value exists (`session.ts:273-277`); design §9 said a present ledger at first load means a copied installation. The engine cannot tell a reinstall from a copy, and a shared id later fails closed (`ledger-diverged`, or `duplicate-installation` when our receipt/seal is in the chain). Acceptable; root must mint a fresh installation id after `duplicate-installation` because re-enrollment alone keeps the shared ledger.
- `publish()` in `github.ts:458-470` reads candidate and receipt commits before `updateRefs`; a transient read error there is reported as `unconfirmed`, costing one seal and a republish. Correct, just wasteful.
- `#transact` records `phase: "dispatched"` before the only dispatch (`session.ts:685-696`); design's `prepared` phase was dropped, so a crash after the save but before the request costs a seal round. Correct.

## What I traced and found sound (with evidence)
- Settlement state machine `session.ts:795-839`: receipt ⇒ accept; own seal ⇒ cancel (anchor := seal and operation := null in one save, `:875-881`); anchor ⇒ create seal, save, then dispatch (identity durable before first dispatch; reused on every retry, R4 and the existing seal-identity test); anything else fails closed. `#accept` moves the anchor and promotes in one save (`:858-872`), so a lost save re-reads the receipt on restart.
- Atomic CAS fence: a delayed publication delivered after its seal can never land, including after a restart that never dispatched the seal (R4 both orders), and after later operations (existing test, R8 late deliveries).
- No replay: the candidate is dispatched exactly once (`:694-696`); `#resume` only settles; a cancelled round re-plans a new candidate; a rewound accepted candidate pauses `history-rewritten` and is never republished (existing tests at 713 and 1126; R8 branch has no duplicate commits across 400 runs).
- Legacy settlement never seals, never republishes (`:842-856`; existing test counts).
- `parseState` enforces anchor == ledger anchor for ledger publications, distinct identities, preimages and incoming bytes for every step, and referenced blobs (`state.ts:560-583, 639`).
- `github.ts`: `acknowledged` only on a validated `clientMutationId` echo with no `errors` (`:445-457`); `readLedger` throws on any malformed answer instead of claiming absence (`:478-488`); `ZERO_OID` encodes an absent anchor; receipt/seal parents and trees are validated before dispatch.
- Native ingestion: verify → pin → hold → save → ack; ack failure leaves ids unacknowledged and re-ingestion is idempotent (existing test 1774); `requiredPath` guards `apply`-returned issues (`:1052`).
- Reconcile with holds: held paths are `untouched`, keep `r` in the target, produce no outgoing or incoming step, and are excluded from rename and bulk logic (`reconcile.ts:193, 209-225, 303`). A decided hold with `chosen == null` plans an exact delete step with the decision id; `#applySteps` writes a held path only for a decision step (`session.ts:954`) and releases only on `applied` (`:963-966`) or when the chosen version is already live at capture (`:594-601`, saved on every path below it).
- Test replacement claims in the `git-session.test.ts` header hold up: the v2 observation/approval tests are replaced by exact-CAS behaviour that R5b reproduces directly (a write between capture and apply is never overwritten), and the deletion-review tests by the bulk guard, which R7/R9b exercise. The gap is F4, which the header does not mention.

## Suggested additional tests for the worker
1. Decide a hold from the first `needs-decision` outcome without a restart and expect `synced` (F1); and after an unrelated apply completes while a hold exists.
2. Stale ledger reads: `absent` once after a landed publication, and "older" twice, must settle on the next fresh read, not pause (F2).
3. `/2` legacy publication with `head == parent`: expect a fence commit on the branch, no review, and `deliver()` of the modelled legacy request returning `false` (F3; flip the current "documented hazard" assertions).
4. Whole top-level folder vanishes below the bulk floor → `VaultCaptureError` (F4).
5. A malformed issue beside a valid one: the valid one is ingested, the bad one is reported, sync does not throw (F5).
