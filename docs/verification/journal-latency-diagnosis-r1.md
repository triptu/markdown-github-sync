# Android configuration apply latency diagnosis (read-only, r1)

## Finding

The observed delay is consistent with serial, repeated verification of **32 distinct journal content objects**, not a blocked native transaction. The supplied pre-apply record has 32 `blobs` entries and 32 different `journalBlob` hashes, with two deferred configuration paths. The root's Android trace reports approximately 200–300 ms for each metadata `exists`/`read`; its latest journal sequence 209 has both steps applied. I did not access the Android device, remote, vault, or source files.

Production `FileJournalStore.load()` calls `records()` and recursively `unpack()`s the latest record. `unpack()` awaits each object read and SHA-256 check one after another (`plugin/src/git-sync/store.ts:97–120,143–162`). Every changed `save()` calls `assertHead()`, recursively `pack()`s the entire state, calls `assertHead()` again, and only then commits a record (`store.ts:222–235`). `pack()` checks each content object with `exists` plus a full `read`, serially (`store.ts:52–95`). Thus the current state pays for all 32 objects on every load and save even when the step changes only a status field. The reverted per-operation duplicate cache premise does not apply to this fixture.

The engine preserves required durability boundaries: `applyConfiguration()` saves exact approved steps before any native write (`plugin/src/git-sync/session.ts:485–526`); `#applyConfigurationSteps()` saves after each of two step outcomes and again after clearing the operation (`session.ts:1719–1767`). Its `#save()` clones and sends a full state to the store (`session.ts:2252–2270`). The public preview, apply, and post-apply panel rendering each enter through a fresh store load (`session.ts:455–460,485–488`; `plugin/src/main.ts:740–750,822–850`). Native `apply()` has its own transaction journal saves, which add time but do not explain these main-journal object reads (`plugin/src/git-sync/obsidian-vault.ts:571–607`; `native-transactions.ts:287–333`).

## Reproduction

I used the production `FileJournalStore` imported directly from the repository with an in-memory `JournalFiles` adapter delayed 225 ms per call. The supplied record's field/recovery shape and 32 distinct blob keys were retained; the 32 missing content bodies were replaced with 32 distinct synthetic strings, then seeded by production `save()`. The synthetic bytes are **not** a valid engine/Git state, so this reproduces store behavior and adapter call counts, not a full engine run. Scripts are `/tmp/journal-latency-bench-r1.ts`, `/tmp/journal-latency-parallel-r1.ts`, and `/tmp/journal-latency-parallel4-r1.ts`; no repository file was changed.

| Load latest state | 8.816 s | 3.394 s | 2.490 s | 5 exists, 1 list, 33 read = 39 |
| Changed save, first step | 18.304 s | 7.459 s | 5.651 s | 43 exists, 2 list, 34 read, 1 write, 1 rename = 81 |

The unchanged call counts show that the prototype still reads and verifies every object on each operation. Its only speedup is overlapping independent object I/O. A two-step apply has at least four engine saves (approval, each step, retirement). With one apply load and one post-apply panel load, the store-only model is about **90.8 s serial**, **36.6 s at four workers**, or **27.6 s at eight workers** at 225 ms/call, before native journal work, capture, repository calls, and any additional UI loads. For these fixed call counts, serial load/save contribute approximately 7.8–11.7 s / 16.2–24.3 s at the observed 200–300 ms range. This is a model, not an Android timing claim; an adapter that internally serializes concurrent requests can erase the overlap benefit.

## Recommended smallest change

Use a bounded worker pool (start with eight for this 32-object case) **within each `FileJournalStore.pack()`/`unpack()` operation** for independent content objects. Keep the outer `serialize()` queue, both head checks, SHA-256 verification, immutable object `put()` verification, and final record write in their existing order. Preserve enumeration order when constructing the packed JSON. When multiple entries name the same object path, schedule that path once or serialize those same-path puts; this avoids concurrent writes to one target but is only a safety detail, not the performance premise here. On any worker error, stop launching new object work and **await all already-started workers** before rejecting, so no write outlives its save and races the next queued operation. Do not carry object values or verification results across operations without a separate invalidation proof.

At eight workers, no more than eight content-object operations are in flight. For `N` existing distinct blobs of roughly equal adapter latency `L`, the serial object portion is `N·L` for load and `2N·L` for save; the bounded ideal is `ceil(N/8)·L` and `2ceil(N/8)·L`, plus unchanged serial directory/head/record work. For this fixture that is 32 reads reduced to four waves on load, and 64 object calls reduced to eight waves on save. The actual worst case remains the present serial latency if the adapter queues internally. Eight simultaneous large base64 objects can raise peak memory; verify on the Android lab, and reduce to four if memory pressure appears (measured here at 3.4 s/load and 7.5 s/save). Do not remove per-save reads merely because an object was verified on the previous load: that weakens the current corruption-detection contract.

## Behavioral checks and remaining gate

The scratch eight-worker prototype passed: exact round-trip; corrupt object rejected on load; corrupt object rejected on save with no new record; stale writer rejected; injected existing-object read failure left the prior record current; injected new-object commit failure left the prior record current. The worker pool drains started tasks before rejection. These are focused checks, not a production patch. A production change should run the existing `plugin/test/journal-store.test.ts` interruption matrix, add a failure case while several distinct new object puts are active, and confirm same-path duplicate content cannot race. The decisive deployment gate is an Android adapter trace showing actual overlapping `exists`/`read` calls, bounded peak concurrency, and a shorter reviewed two-file apply. The root owns that device validation.
